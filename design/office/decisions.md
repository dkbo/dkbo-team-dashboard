## A. 狀態與顏色

### Q1 「思考／執行工具／寫回覆」三種要不要用不同顏色？
**定案（照建議）：都用 ok 綠**，靠圖示（三點泡泡／Terminal＋工具名／鉛筆）、文字與角色動作區分。
理由：三種都是「正在動」；unify 原則「顏色只講狀態」，只有五種語意色，再拆就得拿 info 紫當「思考」，紫色已經是「中性事件、規劃中」。
其他選項（未採用）：思考用 info 紫（三種一眼可分，但違反 unify §1.4 的判準）。

### Q2 「錯誤」（這輪 API／工具出錯停下）用什麼色？
**定案（照建議）：danger 紅，與「等你」同級**（實心紅標記＋地面紅圈，不脈動；只有「等你」脈動）。
理由：錯誤後 session 停在那裡等人重送，符合 danger「不處理就停住」；用脈動與否區分兩種紅，「等你」仍是最搶眼的。
其他選項（未採用）：warn 琥珀（會自己重試的錯誤才適合，但 Claude Code 出錯後不會自己重試）。

### Q3 「中斷」（按 Esc 或被打斷）用什麼色？
**定案（照建議）：warn 琥珀＋■ 圖示，10 分鐘沒新動作就轉成閒置。**
理由：這輪沒做完、可以晚點處理，符合 warn「部分失敗、可晚點處理」；轉閒置避免一整排琥珀。
其他選項（未採用）：直接 idle 灰（多半是自己按的 Esc，不需要提醒；但會跟真的閒置分不出來）。

### Q4 頭頂標記用 DOM 疊層（CSS2DRenderer）還是 3D 貼圖（Sprite）？
**定案（照建議）：DOM 疊層。**
理由：直接用 Tailwind token 與 StatusPill 樣式、亮暗自動換色、字清楚、可 tab 聚焦與螢幕報讀；人數 ≤ 40 時效能沒問題，> 40（擴張第三階）閒置角色本來就不畫標記。
其他選項（未採用）：Sprite（大量時較省，但要自己畫字、無障礙要另做）。

## B. 場景與行為

### Q5 辦公室依什麼分區？
**定案（照建議）：每個「有進行中 dkbo 任務」的專案一區；區內每個任務一組桌群（leader 大桌＋成員 2 × N）；不屬於任務的 session 坐前排「散座區」；完成的人去「休息區」。**
理由：使用者想的是「哪個任務卡住、誰在等我」，任務桌群讓同一任務的人坐在一起；座位依 brief 成員順序固定，位置本身就是記憶點。
其他選項（未採用）：只依專案分區、不分任務（任務多時同一區很亂）；依角色分區（看不出任務）。

### Q6 「無任務 session」（一般 claude／codex、chore-*）放哪？
**定案（照建議）：共用散座區**，依專案名排序；hover 卡寫出專案。
理由：專案區只跟著任務長，大小穩定；散座 session 來來去去，放專案區會讓專案區一直變形。
其他選項（未採用）：放進各自專案區的角落（專案感較強，但沒有任務的專案也得開一區）。

### Q7 「完成」的人要不要離開座位去休息區？
**定案（照建議）：要，待 10 分鐘後走回座位轉閒置。**「等你」「錯誤」永遠留在座位。
理由：參考專案的做法，畫面上「剛做完」一眼可見，也讓座位區只剩還在動的人；10 分鐘是「剛完成」的合理窗口。
其他選項（未採用）：留在座位只換標記（畫面較靜，但完成與閒置的差別只剩標記）。

### Q8 閒置多久算「下班」不畫？
**定案（照建議）：2 小時。** 下班的人不畫角色，工具列／清單底部顯示「N 位已下班 · 顯示」。
理由：herdr 裡常留著幾天前的 session，全畫會把辦公室塞滿閒置的人。
其他選項（未採用）：1 小時；或永遠畫（靠 55% 透明區分）。

### Q9 Claude 與 Codex 在場景裡要不要長得不一樣？
**定案（照建議）：不區分外觀**，靠工具列 kind 篩選與 hover 卡／詳情的 kind Tag。
理由：外觀已經用來分「角色」（leader 皇冠、各 role 固定 Kenney 角色），再疊一層 kind 區分會太雜；需要分時一鍵篩選比較快。
其他選項（未採用）：Codex 用另一組 Kenney 角色模型；或桌上螢幕背面貼 kind 小標。

### Q10 人變多時怎麼擴張？
**定案（照建議）：三階**——≤ 12 人單排；13–40 人專案區兩排、房間加深；> 40 人或 > 6 專案分樓層（工具列「1F｜2F｜3F」，有等你的樓層加紅點），閒置角色不畫改立牌。
理由：單一大房間在 40 人以上鏡頭得拉很遠，角色只剩幾個像素；分樓層保留「一眼看完一層」的尺度。
其他選項（未採用）：無限加深單一房間＋小地圖。

### Q11 窗外光線跟著主題還是本地時間？
**定案（照建議）：跟 dashboard 亮暗主題。**
理由：頁面與場景同一個色調，使用者切主題時一起變；參考專案跟本地時間，但我們的 dashboard 已經有主題鍵。
其他選項（未採用）：跟本地時間（晚上自動夜景，但亮色主題配夜景會很怪）。

## C. 頁面與導覽

### Q12 「辦公室」放導覽列哪裡？
**定案（照建議）：總覽之後（總覽｜辦公室｜歷史｜趨勢｜herdr｜git）。**
理由：它跟總覽一樣是「現在發生什麼」的即時視圖，跟歷史、趨勢這類回顧頁分開。
其他選項（未採用）：放 herdr 旁邊（都是 session 視角）。

### Q13 桌機要不要提供「3D｜清單」切換？窄螢幕預設？
**定案（照建議）：桌機提供切換（記在網址 `view=list`）；< 768 預設清單，可按「仍要開 3D」；768–1023 用 3D，詳情改底部 Sheet。**
理由：清單本來就要做（無 WebGL 的退路），給桌機使用者當「快速看誰需要我」的模式幾乎零成本；手機上 3D 很難點中小人。
其他選項（未採用）：只在無 WebGL 時出清單（需求說「只做 3D」的字面意思）。

### Q14 「等你」要不要額外提醒（分頁標題、瀏覽器通知）？
**定案（照建議）：分頁標題前綴「(2) 需要你 · 」；瀏覽器通知沿用 TopBar 既有的通知鈴開關，新增「有人等你／出錯」兩種事件。**
理由：參考專案有分頁標題計數與完成通知；我們已有通知鈴，不另做設定頁。
其他選項（未採用）：不做通知，只靠畫面。

## D. 資料契約（設計只列需要的欄位）

### Q15 細狀態與現有 PaneStatus 怎麼對應？需要哪些欄位？
**定案（照建議）對應**：`thinking`／`running`／`writing` → `working`；`waiting` → `blocked`；`error` → `blocked`；`interrupted` → `idle`；`done` → `done`；`idle` → `idle`。細狀態另開欄位，不改 `PANE_STATUSES`（TopBar「N 個卡住」會因此把錯誤也算進去——這是建議的效果）。
**設計需要的欄位**（每個 session）：`paneId`、`kind`（claude／codex）、`sessionId`（resume 用）、`substate`、`substateSince`（計時）、`turnStartedAt`、`tool`（名稱＋參數摘要 ≤ 80 字）、`question`（等你時的問句／審批提示）、`error`（錯誤第一行）、`project`、`task`（dir＋名稱＋波）、`member`（role、name；leader 標記）、`model`、`ctx`、`cost`、終端最後 6 行（詳情窗，可沿用 herdr 縮圖的資料）。
補充：Claude Code 不把權限審批寫進 JSONL，所以「等你」要由 herdr 的 `blocked` 加 JSONL 合算；`question` 欄位來自 herdr 畫面。
理由：設計稿上每個顯示都對得到欄位；欄位怎麼來（hook、轉錄檔、herdr 畫面解析）不是設計能決定的。
其他選項（未採用）：error 另立粗狀態（要改 shared 型別與 TopBar 規則）。

## E. 第二輪：效能、頁面物件、互動事件、角色識別（2026-10-24 定案）

### E1 大廳（頁面物件）放房間哪裡？【定案（照建議）】
**定案：房間右側加寬 4.4 格當大廳**（房間 20 → 24.4 × 14）：後牆監控牆、中段檔案室書櫃與 git 檔案櫃、前段立式公告板；電表放休息區茶水台旁、白板放各任務桌群左前方。
理由：既有座標全部不動；左上角是找人清單、右上是狀態計數，右側中下段在預設鏡頭下是空的，不會被疊層蓋住。
其他選項（未採用）：左側加大廳（被找人清單擋住）；另開一間「大廳」房間（要切換，失去一眼看完）。

### E2 頁面物件標籤要不要常駐？【定案（領導修正版）】
**定案：常駐，但預設視角只留最少資訊，並加碰撞規則。**
- 預設視角（fit 全部）用 compact：**只留圖示＋主數字**，有異常（danger／warn）才加 chip；白板 compact 是圖示＋「2/5」，不畫進度條，ESCALATE 縮成 18 圓「!」。
- 拉近到 ≥ fit 距離 × 0.8 才用 full（頁名＋數字＋單位＋chip）；< 0.6 倍只留有異常的物件。
- 碰撞：物件標籤與角色標記（AgentMarker、星數、事件「!」）重疊時，**物件標籤讓位**——先縮成 12 圓點（popover 底＋語意色框），點也壓到就整個隱藏；角色標記之間互撞時，優先序低的縮成 8 色點（hover／選取中的人最優先，其次照 §1.2 狀態優先序）。區牌（ZoneSign）位置固定，擺放時就要避開。
- **預設視角下任何標籤不得互相壓到、不得被 canvas 邊或疊層（找人清單、狀態計數、圖例、縮放鈕、hover 卡）切掉**；稿以此為驗收（`page-office-light`／`dark` 的碰撞檢查皆為 0）。
理由：原建議（compact 仍帶頁名單位與 chip）在預設視角太擠——`page-office-light` 上白板「波 1/3」壓到角色、atlas 區牌與 Bash 標記被切、電表／監控牆／檔案室標籤擠在「錯誤」旁。角色比物件重要，碰撞時讓物件退。
為了讓預設視角乾淨，稿同時調了位置：公告板移到 (21.0, 11.4)、電表移到休息區 (14.0, 8.4)、「無任務 session」與「休息區」區牌移到各區前緣、designer 移到沙發區，暗色預設鏡頭下移 24 px 讓 atlas 區牌不被狀態計數蓋住。
其他選項（未採用）：原建議（compact 帶 chip 與單位，無碰撞規則）；只在 hover 顯示；永遠 full。

### E3 白板的「卡住」與「ESCALATE」怎麼算？【定案（照建議）】
**定案：danger＝桌群內有人等你／錯誤，或 dk-watch 的 BLOCKED／TIMEOUT 尚未解除；warn＝有 ESCALATE 還沒有對應的 DECISION／ruling。兩者並存時白板面與框用 danger，chip 兩個都列。**
理由：沿用 unify 判準（ESCALATE 一律 warn）；白板是任務層的摘要，遠景時看白板就知道哪組卡住。
其他選項（未採用）：白板只反映 dkbo 流程（不看細狀態的等你）——但等你是使用者最在意的。

### E4 電表「跳電」的條件？【定案（照建議）】
**定案：任一 kind 熔斷就跳電（warn，同 TopBar 熔斷 StatusPill）；額度 ≥ 80% 只加 warn chip「額度 84%」，不跳電。** 跳電不變紅。
理由：跟 TopBar 同一份資料、同一個語意，使用者不必學第二套規則。
其他選項（未採用）：只有辦公室裡有 session 的 kind 熔斷才跳電（更貼近畫面，但會跟 TopBar 不一致）。

### E5 git 檔案櫃燈顯示哪一項？【定案（照建議）】
**定案：所有專案加總後只亮最嚴重的一項：衝突（danger）＞ 未推送 commit（warn）＞ 未提交改動／detached（warn）；乾淨熄燈。**
理由：一顆燈只能講一件事；衝突是 unify 定義的 danger。
其他選項（未採用）：三顆燈分別亮（衝突／未推送／未提交）——資訊多但遠看分不清。

### E6 reviewer 被派出時怎麼走（多 dev）？【定案（照建議）】
**定案：本波只有 1 位 dev → 走到該 dev 桌右側；≥ 2 位 → 走到任務白板前，拿板子站著，直到 verdict。**
理由：dkbo 的審查對象是整波差異包，不是逐人；多 dev 時巡桌會暗示一個不存在的順序，而且路程長、遮擋多。
其他選項（未採用）：依 brief 成員順序逐桌巡（熱鬧，但時間長、語意不對）；永遠走到白板（一致，但 1 位 dev 時少了「被審」的指向感）。

### E7 事件動畫要不要重播？【定案（照建議）】
**定案：不重播。只播 SSE 即時收到、ts 在 10 秒內的事件；首次載入、重連、背景分頁切回時直接畫最終狀態。**
理由：效能（背景分頁停 render）與正確性（補播一串過期事件會誤導「現在發生什麼」）。
其他選項（未採用）：切回分頁時快轉播最近 3 個事件。

### E8 任務結案後桌群怎麼收？【定案（照建議）】
**定案：慶祝 3 秒後白板顯示「🎉 結案 ✓」保留 10 分鐘，之後桌群收掉；還開著的 session 移到散座區。abandoned 不慶祝。**
理由：跟 Q7「完成待 10 分鐘」同一個窗口；Q5 規定只有進行中任務才有桌群。
其他選項（未採用）：立即收掉（看不到結案）；保留到使用者手動關。

### E9 職等用襯衫色還是名牌？【定案（照建議）】
**定案：襯衫色（rank-senior 深靛 → rank-mid 藍 → rank-junior 淺天藍，明度由深到淺；訪客淺灰＋白色識別證）。文字只出現在 DOM（hover 卡、詳情、清單的 RankTag「資深 · opus/medium」）。**
理由：遠景看得出的只有大面積顏色；明度階讓色弱也分得出；避開 ok 綠、warn 琥珀、danger 紅，不跟狀態色撞。Kenney 衣服貼圖換成四張職等版本，每職等一份共用材質（效能見 §4.7）。
其他選項（未採用）：3D 胸前名牌（遠景看不清）；頭頂 DOM 名牌（頭頂已有標記＋星，會擠）。
注意：這會改 DESIGN-SYSTEM §1.3「角色衣服用 Kenney 原色」——角色模型（各 role 固定 Kenney 角色）不變，只換衣服顏色；Q9（不分 Claude／Codex 外觀）不受影響。

### E10 Codex 的 model 怎麼對到職等？【定案（照建議）】
**定案：依序比對、第一個命中：`*-mini`／`*-nano` → 初階；`*-codex-max` → 資深；`*-codex` → 中階；`gpt-<版本>`（無後綴的旗艦，例如現在 dkbo 用的 `gpt-5.5`）→ 資深；其他／讀不到 → 訪客。** effort：`minimal` 與 `low` 都是 1 星，`medium` 2、`high` 3、`xhigh` 4；Codex 沒有 max。
理由：dkbo 的 codex kind 目前只有 `gpt-5.5`，它是 Codex 的旗艦，對 opus；規則寫成後綴比對，新版號不用改表。
其他選項（未採用）：gpt-5.5 歸中階（對 sonnet，理由是價位）。

### E11 effort 星數什麼時候畫？【定案（領導修正版）】
**定案：場景裡只在 hover／選取時畫，其他時候都不畫**（不分鏡頭距離、狀態）；找人清單、hover 卡、詳情窗、清單模式照常顯示星數。讀不到 effort 不畫。
理由：原建議（預設畫、compact 隱藏）會讓預設視角每顆頭上多一排星，加重 E2 的擁擠；比較 effort 是點人之後才需要的資訊，DOM 清單已經都有。
其他選項（未採用）：原建議（預設畫、< 0.8 隱藏）；永遠畫。

### E12 找人清單第三組放什麼？【定案（照建議）】
**定案：「完成 · 中斷 · 閒置」併成一組、預設收合（同清單模式 §4.5 的第三欄）；下班的人只在底部計數。**
理由：人要的三組是需要你／工作中／完成；中斷、閒置不需要處理，單獨一組只會拉長清單。
其他選項（未採用）：第三組只放完成，中斷／閒置第四組。

### E13 找人清單的篩選要不要影響場景？【定案（照建議）】
**定案：只縮清單，不改場景；場景篩選仍用工具列的 kind／專案。**
理由：找人是導航（點了飛過去），場景同時變淡會讓人以為別人不見了；兩套篩選各管各的，不互相覆蓋。
其他選項（未採用）：清單篩選＝場景篩選（共用網址狀態，工具列專案 Select 拿掉）。

### E14 on-demand render 下，「等你」的脈動放哪？【定案（照建議）】
**定案：移到 DOM：alert 標記外加 CSS 脈動環（`motion-alert-pulse` 套在標記上），3D 地面紅圈改成靜態雙圈。**
理由：CSS 動畫不需要 WebGL 幀，場景可以完全靜止（0 幀）；Q2「只有等你脈動」不變，只是換到 DOM。
其他選項（未採用）：保留 3D 地面脈動，有人等你時 render loop 以 20 fps 持續跑。

### E15 角色的持續動作（打字、揮手、呼吸）怎麼跟「靜止時不 render」共存？【定案（照建議）】
**定案：細狀態改變時播該 clip 6 秒，之後停在關鍵影格（同 reduced motion 的影格）；hover／選取中的角色持續動；思考三點、等你脈動是 DOM CSS，照常動。**
理由：人要求「動畫只在有狀態變化或互動時跑」；6 秒足夠看出「他剛開始做某事」。
其他選項（未採用）：持續動作以 10 fps 低頻跑（畫面較活，但永遠有幀）；全時循環。

### E16 r3f 下 DOM 疊層用 drei `<Html>` 還是自建一層？【定案（照建議）】
**定案：drei `<Html>`（每個標記一個，`zIndexRange` 分三層：物件標籤 < 一般標記 < alert 標記），不另外接 CSS2DRenderer。** Q4（DOM 疊層）不變，只是實作手段。
理由：r3f 生態內建、隨 `invalidate` 更新位置、frameloop demand 下不額外耗幀；≤ 60 個 DOM 節點沒有效能問題。
其他選項（未採用）：自建單一 overlay（一個 `useFrame` 投影所有座標，元件少一層 portal；> 40 人時較省）。
